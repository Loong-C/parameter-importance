# 证据有效性、沿用与最小重验政策

版本：1.0（2026-08-14）

本政策适用于所有 Stage、Gate、测试、实验、交付和多端同步。它解决两个不同问题：

1. 某份证据是否仍能支持原来的结论；
2. 当前代码是否需要重新执行产生该证据的任务。

两者不得简化为“当前 HEAD 是否等于生成 HEAD”。若旧计划、runbook 或工作日志要求仅因提交变化而整链重跑，以本政策为准。

## 1. 身份模型

每份正式证据至少绑定：

- `producer_commit`：实际生成证据的 Git 提交，不可改写；
- task/Gate、配置哈希和实现/合同版本；
- 数据、模型、checkpoint、seed 和其他输入的内容身份；
- 环境、设备和时效性状态；
- 产物路径、内容哈希、状态和生成时间。

后续使用旧证据时另记：

- `consumer_commit`：当前消费证据的提交；
- `changed_paths` 和语义影响分类；
- 仍有效、需要刷新和已经失效的最小 Gate/单元；
- 针对性验证与判定时间。

`producer_commit != consumer_commit` 是正常状态，不是失败。Git 提交用于追溯源码；证据是否有效由相关依赖和内容身份决定。

## 2. 证据类型与失效键

| 证据类型 | 主要失效键 | 不会单独使其失效的变化 |
|---|---|---|
| 内容寻址资产 | revision、文件集合、大小/哈希、预处理合同 | HEAD、文档、日志、下游代码 |
| 环境构建 | lock/wheel、Python/ABI、构建脚本、关键运行库 | 报告、计划、无关业务代码 |
| 硬件健康快照 | 设备 UUID、驱动/内核、ECC/row-remap、拓扑、有效期 | 模型代码、文档；到期只刷新快照 |
| 数值/训练结果 | 生产该结果的实现语义、配置、输入、seed、精度、设备合同 | consumer、报告或下游代码变化 |
| 测试/Gate | 被测实现、测试合同、fixture、阈值和所引用证据 | 无关 Stage、worklog、同步状态 |
| 派生表/图/报告 | 权威源表及派生代码/参数 | 原始运行无关的文字修改 |
| 同步/交付观察 | 被观察端、目标提交、工作树和观察时间 | 既有科学结果本身 |

时效性状态过期时标记对应状态为 `STALE`，只刷新该状态及直接依赖它的检查。不可变内容哈希仍匹配的资产和科学结果不随之自动失效。

## 3. 变更影响分类

从 `producer_commit` 到 `consumer_commit` 的每项变化必须归入以下一类：

| 类别 | 默认动作 |
|---|---|
| 元数据：worklog、注释、格式、说明文字 | 沿用证据；运行文档/链接检查即可 |
| 下游/consumer-only | 沿用上游证据；测试当前 consumer |
| 观测或交付代码 | 保留科学证据；只重做观察/交付检查 |
| 测试或阈值 | 原始实验结果保留；重验受影响测试/Gate，不重做无关实验 |
| 派生代码 | 保留权威源数据；重建受影响派生产物 |
| 生产实现/合同 | 只使依赖该语义的单元及其下游失效 |
| 配置/输入/seed/资产身份 | 只使消费相应身份的单元及其下游失效 |
| 环境/硬件 | 按实际依赖刷新环境或设备层；不扩大到 CPU、资产或无关 Stage |
| 无法判定或证据损坏 | 对最小不确定闭包 fail closed；先补审计，不默认整链 |

共享文件发生变化时必须审查实际 diff 和调用路径，不能仅凭“这是公共模块”宣布全部 Gate 失效。若同一修改只改变某个 consumer 的解析、显示或编排行为，上游 producer 证据继续有效。

## 4. 沿用判定

沿用旧证据必须同时满足：

1. 原始产物、索引和哈希可读取且内部引用闭合；
2. 原 Gate 在生成时有效，且没有未解决的正确性失败；
3. 配置、输入资产、seed 和相关环境身份未发生影响该结论的变化；
4. 时效性检查仍有效，或已单独刷新；
5. 差异已分类，未分类变化不进入“沿用”结论；
6. 对 consumer 修复或测试合同变化已运行针对性回归；
7. 日志记录生成提交、消费提交、保留 Gate、刷新 Gate、失效 Gate和理由。

沿用不是复制或重写旧产物。旧证据保持原路径和 `producer_commit`，新的兼容性/沿用记录作为独立证据引用它。

## 5. 失败恢复与重验算法

失败后依次执行：

1. **冻结现场**：保存 attempt ID、退出码、最后有效日志、已发布分片/checkpoint 和活动进程状态；不覆盖旧目录。
2. **分类根因**：输入、生产实现、consumer/编排、验证合同、环境/硬件、基础设施暂态或未知。
3. **确定最近安全边界**：不可变发布、shard commit、checkpoint commit、attempt commit state 或权威源表。
4. **列出影响闭包**：明确保留、刷新、失效的单元；默认最小闭包。
5. **先验证修复**：运行单元测试、fixture、dry-run/preflight 和一个最小代表单元。
6. **恢复正式执行**：从最近安全边界继续；派生产物从权威源重建；只有不可恢复单元才重新开始。
7. **设置停止条件**：相同输入/环境下的一次暂态重试仍失败后，不得继续机械重试；必须获得新诊断或新修复。

任何“重跑计划”都必须写出：重跑单元、保留单元、原因、入口、预计资源、最大尝试次数和停止条件。没有这些信息不得启动昂贵重跑。

## 6. 允许整链重跑的条件

整 Stage 或整链重跑是例外，只在以下至少一项成立时允许：

- 基础配置、核心数学合同、输入资产/seed 方案或生产实现改变，影响闭包确实覆盖整链；
- 权威索引、哈希或 lineage 损坏，无法证明任何可恢复边界；
- 环境/硬件变化会影响整链中的每个相关数值单元，且不存在可分层刷新方案；
- 独立审计发现系统性污染、选择性缺失或错误复用，无法隔离到更小范围；
- 用户在看到范围、成本和替代方案后明确要求完整重放。

以下情况不得单独触发整链重跑：HEAD 改变、追加 worklog、修改计划/报告、同步端不同 HEAD、G10/交付 consumer 缺陷、单个测试失败、SSH 中断或硬件健康快照到期。

## 7. 同步和 Gate 语义

- 服务器运行前只要求其检出声明的 `execution_commit` 且工作树干净；不要求所有端长期同 HEAD。
- Gate 汇总可以引用由不同 producer commit 生成的证据，但必须记录各自身份和兼容性判定。
- 最终 readiness 表示列出的证据集合对声明范围有效，不表示仓库以后不能变化。后续变化只触发影响分析；未受影响的 readiness 组成证据继续可用。
- 文档、同步和下游开发可以与只读证据核验并行；消费前置 Gate 输出的任务仍按数据依赖串行。

## 8. 禁止事项

- 禁止把提交号相等当作内容相等或科学有效性的充分条件。
- 禁止把提交号不等当作证据失效的充分条件。
- 禁止覆盖失败证据、清空输出目录后伪装成首次运行或删除仍可恢复的 checkpoint。
- 禁止为了让形式规则通过而重复下载、重建环境、重跑 GPU 训练或容量测试。
- 禁止在没有新信息的情况下连续重复同一失败命令。
